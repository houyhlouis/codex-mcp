# Limitations and alternatives

English | [简体中文](limitations.zh-CN.md)

These are implementation boundaries, not claims that the underlying platforms cannot support more. The investigation compared direct app-server, both official SDKs, batch CLI, the local daemon/proxy and native terminal interaction; see [research](integration-research.md).

| Limitation | What was investigated and why | Compliant partial solution |
|---|---|---|
| **No automatic notifications in every main agent** | MCP progress/prompt capabilities vary; simply emitting notifications cannot force a client to display or process them. | Every event is retrievable through bounded polling, with pending requests included independently of notification delivery. Optional progress tokens and form elicitation work when the client supports them. |
| **No guarantee of every stream delta after broker/backend failure** | Direct stdio has no upstream event replay cursor. Native history can recover persisted turn/items, not necessarily every transient delta. A shared daemon was considered but also requires explicit subscription/replay semantics. | SQLite preserves committed received events. Restart marks a potential gap; resume and page native history. No input or shell action is automatically retried. |
| **No exactly-once execution across a lost control acknowledgement** | A process can fail after Codex accepts a turn but before its response reaches durable storage. An application idempotency key cannot retroactively make an unacknowledged upstream action transactional. | Save operation keys and uncertain outcomes, surface task IDs, reconcile thread history, and require a new instruction after inspection. |
| **Human approvals need a UI or explicit trusted relay** | Elicitation support is optional, and a tool argument claiming human consent is not evidence of it. Same-user shell access also cannot be isolated by a wrapper. | Native `approve_for_me` is now implemented and tested for eligible automatic reviews. Requests still requiring human input can use an MCP prompt, terminal review, or an explicitly trusted relay. |
| **Only one-shot approval scopes** | Installed schemas also offer session approvals and rule amendments. Those are technically possible but expand future authority and can change persistent policy; not exposed in this version. | Approve individual requests through the bridge. Review broader policy intentionally in native Codex; the bridge does not make those changes. |
| **Secret questions and advanced external forms** | Native request schemas can contain secret fields, URL flows or complex JSON Schema. Passing secrets through ordinary MCP model-visible arguments risks transcript leakage; the small validator rejects unsupported schema features. | Use native Codex login or the provider's browser flow, then relay completion without tokens where supported. Simple typed forms and ordinary questions are implemented. A future dedicated secret channel must avoid model-visible content and history echoes. |
| **Custom profiles and dynamic parent tools use experimental fields** | The installed schema requires the experimental capability for named profiles and dynamic tools. Falling back to ordinary workspace-write would lose read confinement; text/PTY parsing would lose typed question correlation. | Version gate at Codex 0.167.0, verify acknowledged profiles, test against the installed schema and fail closed on incompatible versions. Use ordinary follow-up text if a future version temporarily lacks a parent-tool feature, after adapting and testing the integration. |
| **Some toolchains outside system directories need configuration** | Strict project read access initially prevented a standalone Codex binary under the home directory from executing. Broad home access would expose unrelated projects and credentials. | Exact Codex binary access is included; operator-approved `toolchain_paths` adds specific read-only runtime/dependency paths. Standard Python coding/tests passed live. |
| **Wider native account history remains restricted** | Native thread APIs can access more than the approved projects. Arbitrary thread IDs would weaken project and ownership checks. | Scoped session discovery/import is now implemented for an exact approved cwd, with explicit confirmation that other clients stopped the root conversation. Verified native descendants are also supported. Unrelated sessions remain inaccessible. |
| **No Git worktree automation** | Existing worktrees are ordinary selectable project directories. Creating/moving worktrees introduces separate Git mutation and dirty-checkout semantics. | Select existing separate worktrees; multiple tasks in disjoint directories work. Project creation makes directories only. |
| **No native terminal UI or unrestricted shell/PTY passthrough** | The documented `thread/shellCommand` runs outside the sandbox; a generic RPC/terminal proxy would defeat the project boundary. | Scoped image/text attachments, skills, plan mode, review, forks, queues, goals and lifecycle controls are now implemented. Native interactive programs and application-specific UI commands remain in the terminal; ordinary commands can be requested through Codex's sandboxed tool workflow. |
| **MCP 2026-only clients** | Current SDKs offer a new lifecycle and compatibility fallback. This implementation intentionally supports the established handshake protocols and application-level polling rather than adopting all new extensions. | Use a client with legacy fallback (official MCP 1.26.0 tested); a native SDK v2 adapter is a viable future addition, not an inherent impossibility. |
| **Platform/client coverage** | Linux and the actual installed Codex were available. Claude Code, native Windows and macOS were not available. Native Windows IPC/ACL/locking and macOS peer/path handling are now implemented, but were not executed on this Linux host. | Linux remains the locally verified runtime; native Windows/macOS adapters and CI jobs are included. Claude Code setup follows official documentation and the same tested MCP protocol; its UI is not claimed tested. Use Linux/WSL with local Codex where appropriate; WSL itself was not tested. |

Unsupported or unknown server requests receive an error with no permission granted. This includes external credential-refresh and attestation callbacks: the bridge uses the installed CLI's native saved authentication instead. A future deployment requiring those flows needs a separately authorized implementation, not extracted credentials.

Remote access is intentionally absent because this task requires local-only operation. Outbound requests made by Codex to its authorized model service are still necessary for cloud-hosted models.

The current [terminal parity matrix](terminal-parity.md) gives the complete control mapping and explains the remaining native-only operations. Native subagent management and explicit Approve for me are no longer implementation gaps. Native child threads that advertise no direct-input capability are controlled through their parent rather than bypassing that restriction. Native queue entries can be consumed before an update arrives; that outcome is surfaced, not automatically replayed.

In the tested native runtime, cancelling a child approval interrupted that child but could leave its parent's native wait pending. The child interruption is visible in parent event polling and `family_status` remains active. The main agent can explicitly interrupt the waiting parent and send a follow-up explaining the denial. The bridge does not silently resume the child, override the denial, or invent a child final answer.

Projects are selected dynamically through workdir/project_id rather than configured workspace roots. See [configuration](configuration.md) and [platforms](platforms.md).
